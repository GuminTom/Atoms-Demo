## Context

本项目旨在构建一个多智能体 Vibe Coding 平台，让用户能够通过自然语言与 AI Agent 协作，快速创建、管理和发布个人应用。

**当前状态：**
- 项目处于初始设计阶段，尚无现有代码实现
- 前端将参考 Atoms (https://atoms.dev/dashboard) 的现代化设计布局
- 后端将参考 MetaGPT (https://github.com/FoundationAgents/MetaGPT) 的多智能体架构实现

**约束条件：**
- 前端技术栈：React.js + TypeScript + Tailwind CSS
- 后端技术栈：Golang + Hertz 框架（DDD 架构）
- 前后端通信：Protobuf IDL
- 需要支持多智能体协作（工程师模式和团队模式）
- 需要支持应用的创建、管理和发布部署

## Goals / Non-Goals

**Goals:**
- 构建一个现代化、易用的 Vibe Coding 平台界面，参考 Atoms 设计
- 实现多智能体协作系统，参考 MetaGPT 架构
- 支持工程师模式（单个软件工程师 Agent）和团队模式（产品经理、架构师、工程师协作）
- 实现完整的用户认证和授权系统
- 提供应用创建、编辑、删除、发布的完整生命周期管理
- 实现项目持久化存储，包括对话记录、代码、配置、日志
- 提供统计信息和最近应用列表功能
- 支持应用的自动部署和访问

**Non-Goals:**
- 不实现自定义的大模型训练能力，仅集成现有大模型 API
- 不实现复杂的 DevOps 平台，仅提供应用部署和基本管理
- 不实现多用户实时协作编辑，初期仅支持单用户使用
- 不实现移动端原生应用，初期仅支持 Web 端

## Decisions

### 1. 前端架构决策

**决策：** 采用 React + TypeScript + Tailwind CSS，参考 Atoms 设计布局

**理由：**
- React 生态成熟，组件化开发适合构建复杂的单页应用
- TypeScript 提供类型安全，减少运行时错误
- Tailwind CSS 提供快速的样式开发能力，适合构建现代化 UI
- Atoms (https://atoms.dev/dashboard) 提供了优秀的 Dashboard 设计参考，包括：
  - 侧边栏导航（Dashboard、Projects、Settings 等）
  - 卡片式布局展示应用列表
  - 现代化的配色方案和交互设计
  - 清晰的信息层级和视觉引导

**备选方案：**
- Vue.js + Element UI：生态成熟，但 React 更适合复杂的状态管理
- Next.js：服务端渲染，但本项目更适合 SPA 架构
- Svelte：编译型框架，性能优秀，但生态相对较小

### 2. 后端架构决策

**决策：** 采用 Golang + Hertz 框架，DDD 架构，参考 MetaGPT 多智能体实现

**理由：**
- Golang 性能优秀，适合构建高并发服务
- Hertz 是字节跳动开源的高性能 HTTP 框架，与 Go 生态兼容
- DDD（领域驱动设计）架构适合复杂的业务逻辑，便于维护和扩展
- MetaGPT 提供了成熟的多智能体架构参考：
  - 多 Agent 协作模式（产品经理、架构师、工程师等）
  - SOP（标准作业程序）驱动的工作流
  - 角色定义和任务分配机制
  - 上下文管理和信息传递

**MetaGPT 核心架构参考：**
- **Role 抽象**：定义不同 Agent 的角色（ProductManager, Architect, Engineer 等）
- **Action 抽象**：定义 Agent 可以执行的操作
- **Environment**：管理 Agent 之间的交互和上下文
- **Memory**：存储对话历史和项目信息
- **SOP**：定义标准作业流程，指导 Agent 协作

**备选方案：**
- Python + FastAPI：MetaGPT 本身是 Python 实现，但 Golang 性能更优
- Java + Spring Boot：生态成熟，但开发效率不如 Golang
- Node.js + Express：JavaScript 全栈，但类型安全不如 Golang

### 3. 多智能体系统设计

**决策：** 实现两种模式：工程师模式（单 Agent）和团队模式（多 Agent 协作）

**工程师模式：**
- 激活单个 **Software Engineer Agent**
- 直接将用户需求转化为代码实现
- 适合简单网站、快速原型、演示项目
- 交互流程：用户描述需求 → Agent 理解 → 生成代码 → 迭代优化

**团队模式：**
- 激活多个 Agent 协作：
  - **Product Manager**：分析需求，生成用户故事、需求文档
  - **System Architect**：设计系统架构、数据结构、API 接口
  - **Software Engineer**：根据架构设计实现代码
- 参考 MetaGPT 的 SOP 流程：
  1. 需求分析（Product Manager）
  2. 架构设计（System Architect）
  3. 代码实现（Software Engineer）
  4. 代码审查（可选）
  5. 测试部署

**Agent 核心能力：**
- 自然语言理解和生成
- 代码生成和修改
- 文件操作（创建、修改、删除文件）
- 上下文理解和记忆
- 工具调用（如 Git、终端命令等）

### 4. 数据存储决策

**决策：** 采用 PostgreSQL 作为主数据库，Redis 作为缓存，对象存储用于代码和文件

**理由：**
- PostgreSQL 支持复杂查询和事务，适合存储用户数据、应用元数据
- Redis 提供高性能缓存，适合存储会话、Token、频繁访问的数据
- 对象存储（如 MinIO 或云存储）适合存储项目代码、构建产物、日志文件

**数据模型概览：**
- **Users**：用户信息（ID、用户名、邮箱、密码哈希、头像、设置）
- **Apps**：应用信息（ID、用户 ID、名称、描述、状态、创建时间、更新时间）
- **AppVersions**：应用版本（ID、应用 ID、版本号、代码快照、创建时间）
- **Conversations**：对话记录（ID、应用 ID、消息列表、创建时间）
- **Messages**：消息内容（ID、对话 ID、角色、内容、时间戳）
- **Deployments**：部署记录（ID、应用 ID、版本 ID、URL、状态、创建时间）
- **Statistics**：统计数据（用户 ID、应用数量、发布数量、访问量、Tokens 消耗）

### 5. API 设计决策

**决策：** 采用 Protobuf IDL 定义 API，支持 gRPC 和 HTTP 双协议

**理由：**
- Protobuf 提供强类型定义，减少前后端沟通成本
- 支持 gRPC（高性能）和 HTTP（兼容性好）双协议
- 便于生成客户端 SDK 和文档

**核心 API 模块：**
- **AuthService**：认证相关（注册、登录、登出、Token 刷新）
- **UserService**：用户管理（获取/更新用户信息、修改密码）
- **AppService**：应用管理（创建、列表、获取、更新、删除）
- **WorkspaceService**：工作空间（获取项目状态、保存代码、获取历史）
- **AgentService**：Agent 交互（发送消息、获取对话历史、切换模式）
- **DeploymentService**：部署管理（发布应用、获取部署状态、停止部署）
- **StatisticsService**：统计信息（获取用户统计数据）

### 6. 应用部署决策

**决策：** 采用容器化部署，使用 Docker + Kubernetes 或简化版方案

**理由：**
- 容器化提供一致的运行环境
- 支持快速部署和回滚
- 便于资源隔离和扩展

**部署流程：**
1. 用户点击"发布"按钮
2. 后端触发构建流程：
   - 收集项目代码和配置
   - 生成 Dockerfile（根据项目类型）
   - 构建 Docker 镜像
   - 推送到镜像仓库
3. 部署到集群：
   - 创建 Deployment 和 Service
   - 配置 Ingress 路由
   - 分配访问 URL
4. 返回部署状态和访问 URL 给用户

**简化方案（初期）：**
- 使用 Docker Compose 或直接运行容器
- 对于前端应用，可直接部署到静态文件服务器
- 对于后端应用，运行独立容器

## Risks / Trade-offs

### 风险 1：大模型 API 成本和性能

**风险：** 大模型 API 调用成本高，响应时间长，可能影响用户体验

**缓解措施：**
- 实现 Token 消耗统计和限制，避免意外高额费用
- 采用流式响应，提升用户感知体验
- 实现对话缓存，对于相似问题可复用之前的回答
- 支持用户配置自己的 API Key，平台不承担 API 成本

### 风险 2：多智能体协作的可靠性

**风险：** 多 Agent 协作可能出现理解偏差、重复工作、进度不一致等问题

**缓解措施：**
- 参考 MetaGPT 成熟的 SOP 流程，明确各 Agent 职责
- 实现严格的上下文管理，确保信息传递准确
- 提供人工干预机制，用户可在关键节点确认或修改
- 实现进度可视化，让用户了解各 Agent 的工作状态

### 风险 3：代码生成的质量和安全性

**风险：** AI 生成的代码可能存在 Bug、安全漏洞、性能问题

**缓解措施：**
- 实现代码审查机制，可集成静态代码分析工具
- 提供代码预览和编辑功能，用户可修改生成的代码
- 实现沙箱运行环境，限制生成代码的权限
- 记录代码生成历史，便于追溯和回滚

### 风险 4：应用部署的复杂性

**风险：** 不同类型的应用需要不同的部署环境，配置复杂

**缓解措施：**
- 预定义常见项目类型的部署模板（React、Vue、Node.js、Python 等）
- 实现自动检测项目类型，选择合适的部署方案
- 提供部署日志和错误诊断，帮助用户排查问题
- 初期支持有限的项目类型，逐步扩展

### 风险 5：数据安全和隐私

**风险：** 用户的代码、对话记录可能包含敏感信息

**缓解措施：**
- 实现数据加密存储（数据库加密、文件加密）
- 实现严格的访问控制，确保用户只能访问自己的数据
- 提供数据导出和删除功能，符合隐私法规要求
- 明确隐私政策，告知用户数据使用方式

## Open Questions

1. **大模型集成策略**：平台是否需要内置 API Key，还是完全由用户配置自己的 Key？
   - 考虑因素：成本、用户体验、合规性

2. **项目类型支持**：初期支持哪些类型的项目？
   - 选项：仅前端静态网站、前端 + 简单后端、全栈应用

3. **部署环境**：使用自建 Kubernetes 集群，还是依赖云服务？
   - 考虑因素：成本、维护复杂度、可扩展性

4. **代码编辑器**：使用 Monaco Editor（VS Code 核心）还是 CodeMirror？
   - 考虑因素：功能丰富度、性能、集成复杂度

5. **实时协作**：是否需要支持多用户实时协作？
   - 考虑因素：技术复杂度、用户需求、开发周期
